# Changelog

All notable changes to `ferry` will be documented in this file.

## Unreleased

- Source schemas and mappings use physical column names directly. Removed redundant column mappings, reference-target metadata and split translation annotations. Built-in labels use `x-ferry-trans` with priority over `title`; `x-ferry-reference` marks native references for SQL storage and text-transform availability.

- A single reversible `create_ferry_tables` migration creates the current schema for fresh installations. Incremental migrations and legacy metadata conversion have been removed.

- Structure adapters are registered by `getKey()` in `StructureAdapterRegistry`; the nullable `Upstream.adapter` selects one explicitly. Without a selection, no structure reading is queued or performed. The upstream form allows choosing an adapter only during creation; the saved selection is read-only during editing.

- Structure preparation state and metadata access belong to `Models\Structure`. `Contracts\Adapter` separates reading from persistence, with `Services\RosettaAdapter` registered as **1C Rosetta** (`rosetta`).
- `StructureItem` stores ready JSON Schemas keyed by physical column names, source keys and generic ordering. Replicas own saved input JSON Schema snapshots, and transformation definitions calculate effective outputs; Rosetta types and composite expansion stay inside the structure adapter.
- Connector-based Origin contract, service-owned persistence and database jobs committed atomically with model changes. Workers serialize each upstream, retry current desired configurations and retain deletion context until external cleanup succeeds. Desired and applied configurations are encrypted separately.
- Mapping and binding state uses a single list of source and static rows. Every source retains its settings and nullable target, and Ferry preserves the row format in `Replica.mapping` with nested `options`; forms and Kafka connectors use the same physical source names.
- Kafka Connect management through `phpinnacle/franz`: one Debezium PostgreSQL source per upstream and one JDBC sink per replica, connector/task status, and policy-backed lifecycle actions.
- Shared source capture retains active and paused replicas. Each sink whitelists its own columns; activation requests incremental snapshots when capture expands to new tables or columns. Replica lifecycle uses only status; editing preserves paused replicas until explicit activation.
- Static destinations registered through `FerryPlugin::destinations()`, with declared logical types, required fields, their own connection and primary key, and fixed values. Ferry never changes their table schemas; sink connectors upsert rows and propagate source deletions by the mapped primary key. Unavailable destinations block saving and activation.
- Transactional dynamic-table updates use `ReplicaTableManager` for schema change planning and `ReplicaSchemaResolver` for effective schemas and keys. Renames preserve values; removals and type changes apply directly on save and discard the affected column data. Structure preparation is queued after commit by `StructureObserver`, ignores superseded runs, imports repeated chunks without duplicates, and preserves published snapshots on failure.
- JSON Schema-based `FieldMapping` with source/static rows, whole-value connections and explicit array-item or object-property collection through `x-mapping`, custom `staticForms()` and standard `withBuiltinStaticForms()` editors, inverse layout, and shared client/server compatibility checks. Compatibility includes enum subsets and integer-to-number widening; directional formats and string length checks are configurable. `canConnectUsing()` adds application restrictions.
- `FieldBinding` supports simple strings, custom child schemas and connected static card pairs enabled by `staticValues()`, with built-in Value inputs, generated editable targets, and shared source settings. Static targets may share source identifiers. Its forms stay visible while unbound, with local binding controls and clickable lines for unbinding. Both components expose independent native `sourceSettings()` schemas for fields and actions, search, containment, `dense()` spacing, `compact()` description tooltips, configurable `columnSpans()`, metadata and warnings.
- Mapping and binding cards display technical names, required markers, formats, enums, nullability and scoped constraints. Array chevrons expand nested item details. Source hints follow `outputSchema()`; unavailable candidate clicks preserve selection, while existing incompatible connections remain visible.
- `Contracts\Transform` unifies editor blocks, input compatibility, output schemas and Kafka connector configuration. Cast, Filter, InsertUuid and the optional Trim, Substring and MaskField implement it directly. `kafka.transforms` lists their classes; the service provider resolves them through the container and registers them in `TransformRegistry`. The fluent `Transformation` descriptor and separate Kafka handlers have been removed.
- One catalog distinguishes field and record transform scopes. Ordered, repeatable field transforms use the standalone `FieldTransforms` chip editor; record transforms use `RecordTransforms` tabs backed by `Replica.transforms` and run first in the sink pipeline. Chips support individual settings, removal, drag ordering and keyboard ordering before connecting or binding. Native forms validate parameters; `accepts()` and `output()` drive menus and previews through complete JSON Schema chains. Built-in value transforms preserve nullability and discard unsupported source constraints; custom transforms can accept arrays or objects.
- Transform parameters are validated by native Filament schemas; input validation uses `TransformRegistry` to check type chains and destination compatibility without compiling connector configurations. Filters use JSONPath predicates scoped to their owning source, capture unbound sources and preserve tombstones. Former `type`/`value` filter settings require reconfiguration. Static values remain native scalar mappings, are inserted into temporary fields, and receive their ordered transforms before final destination projection and renaming.
- Field mappings use JSON Schema directly for compatibility and transform outputs. Cast targets use native Kafka Connect types: `string`, `int8`, `int16`, `int32`, `int64`, `float32`, `float64` and `boolean`. Integer targets produce JSON Schema `integer`; floating-point targets produce `number`. Upstream configuration is encrypted as an array, with driver-owned form fields. Connection tests always disconnect and return sanitized notifications without persisting results. Structure runs track `processed`/`estimated` and use `updated_at` for stale detection. PHP and JavaScript suites run independently without live Kafka.

## 1.0.0 - 202X-XX-XX

- initial release
- `Upstream` model with encrypted credentials, an activity toggle and connection testing
- queued structure preparation storing ready JSON Schemas as `StructureItem` snapshots through a replaceable `Adapter`
- `Replica` model storing the source object, the field mapping schema and the generated destination table name
- Filament `ReplicaResource` mapping published 1C fields onto a physical destination table named `{prefix}{code}`
- destination tables carry a single technical column `idrref` as the primary key holding the 1C row identifier
- mapping changes add, rename and drop columns, and ask for confirmation whenever stored data would be lost
- replicas are paused automatically when a republished structure drops or retypes a mapped field
